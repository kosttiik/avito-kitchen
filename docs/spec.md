# Технический план Avito.Кухни

Это утверждённый до реализации план, предоставляемый как запрошенный в задании дополнительный артефакт. Он сохранён как живой документ: исходные решения не подгоняются под код, а обнаруженные при реализации требования добавляются с критериями приёмки и проверками. Исходное задание остаётся неизменным и имеет абсолютный приоритет.

## 1. Понимание задачи

Исходный источник истины — [`backend-trainee-assignment-autumn-2026.md`](../backend-trainee-assignment-autumn-2026.md). Он полностью прочитан. Файл остаётся неизменным и будет повторно прочитан при финальном аудите.

Канонический репозиторий — `github.com/talense-tasks/backend-trainee-assignment-autumn-2026-kosttiik-4a1f9845`.

Нужно создать MVP платформы заказа еды с двумя сторонами:

- веб-клиент Avito.Кухни находит заведение, просматривает меню, создаёт и отслеживает заказ;
- подключённое заведение публикует меню, получает заказы, принимает или отклоняет их и обновляет состояние.

Решение: модульный монолит для API Avito.Кухни, PostgreSQL и отдельный запускаемый сервис примера заведения. Всё хранится и запускается из одного репозитория через Docker Compose.

## 3. Предлагаемый MVP

### Входит в MVP

- Одно предварительно подключённое демонстрационное заведение типа `restaurant`.
- Закрытый API интеграции с отдельным ключом Bearer заведения.
- Список активных заведений без геопоиска.
- Плоское меню с названием, описанием, ценой и доступностью.
- Полная синхронизация меню заведением.
- Заказ из 1–50 уникальных позиций одного заведения, количество каждой — 1–100.
- Непрозрачный `user_id` основной платформы без локальной таблицы пользователей и аутентификации.
- Адрес доставки как снимок заказа; маршрутизация доставки не реализуется.
- Проверка ожидаемой цены и доступности при создании.
- Ключ идемпотентности для защиты от дублей при повторе.
- Получение заведением заказов через опрос по курсору.
- Принятие, отклонение и смена статуса через отдельный сервис заведения.
- Статусы `pending`, `accepted`, `preparing`, `ready`, `rejected`.
- Полный запуск API, БД, миграций, демонстрационных данных и примера заведения через Compose.

### Не входит в MVP

- Пользовательский интерфейс.
- Аутентификация и авторизация пользователей.
- Публичное самостоятельное подключение заведений и интерфейс администратора.
- Оплата, расчёты и возвраты.
- Курьеры, маршрутизация, расчёт времени и подтверждение доставки.
- Геопоиск, зоны доставки и расчёт стоимости доставки.
- Количественные остатки, их резервирование и распределённые блокировки.
- Заказ из нескольких заведений.
- Категории, модификаторы, комбо, промокоды, отзывы и рекомендации.
- Push-уведомления, Kafka, Redis, вебхуки и отдельный брокер сообщений.
- Отмена пользователем после создания.
- Управление секретами, ограничение частоты запросов и завершение TLS промышленного окружения.

## 4. CJM пользователя

### Основной сценарий

1. Веб-клиент запрашивает список активных заведений.
2. Пользователь выбирает заведение и получает его актуальную проекцию меню.
3. Недоступные позиции остаются видимыми с `available=false`, но клиент не должен позволять добавить их в корзину.
4. Корзина собирается на клиенте и содержит только позиции одного заведения.
5. При отправке заказа клиент передаёт:
   - `user_id`;
   - заведение;
   - адрес доставки;
   - ID позиции меню, количество и увиденную пользователем цену;
   - уникальный `Idempotency-Key`.
6. API в одной транзакции повторно читает позиции, проверяет принадлежность заведению, активность, доступность и ожидаемые цены.
7. При успехе API сохраняет снимок заказа и отвечает `201`, состоянием `pending`, рассчитанной суммой и ID заказа.
8. Пользователь опрашивает заказ или список своих заказов и видит изменения статуса.
9. Заведение принимает заказ либо отклоняет его с понятной причиной.
10. Положительный путь завершается статусом `ready`: заказ готов для внешнего процесса доставки.

### Негативные сценарии

- Заведение или заказ не существует: `404`.
- Некорректный UUID, пустой адрес, количество вне диапазона, дубли позиций: `400 validation_error`.
- Позиция удалена, выключена или стала недоступна: `409 menu_item_unavailable`.
- Цена изменилась после просмотра: `409 menu_item_price_changed` с текущей ценой; клиент обязан показать изменение и повторно подтвердить заказ.
- Позиции относятся к разным заведениям: `409 mixed_establishments`.
- Повтор с тем же ключом идемпотентности и тем же телом возвращает прежний заказ без дубля.
- Тот же ключ с другим телом: `409 idempotency_key_reused`.
- Заведение фактически обнаружило отсутствие товара после создания: заказ может быть отклонён из `pending` с причиной `out_of_stock`.
- Внутренняя ошибка не раскрывает детали SQL или сети; клиент получает стабильный `internal_error` и может повторить запрос с тем же ключом.

## 5. CJM заведения

1. Avito вручную допускает заведение: создаёт ID площадки, связь внешнего ID и выдаёт высокоэнтропийный ключ интеграции. В демонстрационном окружении это делает отдельное идемпотентное заполнение данных.
2. Пример заведения запускается как отдельный процесс и хранит собственное демонстрационное меню в памяти.
3. После готовности основного API сервис отправляет полный снимок меню через `PUT /integration/v1/menu`.
4. Основной API находит заведение по ключу, добавляет или обновляет позиции по `(establishment_id, external_item_id)` и деактивирует отсутствующие в снимке позиции.
5. Изменение цены, названия или доступности через операторский API примера заведения обновляет локальную модель и повторяет полную синхронизацию.
6. Пример заведения периодически запрашивает изменённые заказы по непрозрачному курсору.
7. Заказ содержит ID заказа Avito, ID пользователя платформы, адрес и снимки позиций с внешними ID заведения.
8. Пример заведения создаёт детерминированный собственный `external_order_id` и показывает заказ оператору.
9. Оператор вызывает пример заведения, а тот передаёт в основной API решение `accepted` или `rejected`.
10. Для принятого заказа оператор последовательно выставляет `preparing`, затем `ready`.
11. При недоступности основного API опрос и синхронизация меню повторяются с ограниченной экспоненциальной задержкой. Локальная операция считается успешной только после подтверждения основного API.
12. При недоступности примера заведения новые заказы остаются в PostgreSQL в `pending`; после запуска сервис дочитывает их с начала или с последнего курсора.

## 6. Предметная модель

### Заведение (`Establishment`)

- UUID, которым владеет площадка.
- Поля: имя, тип `restaurant|cafe|store`, описание и признак активности.
- Создаётся вне публичного API; универсального CRUD нет.
- Физическое удаление не используется.

### Интеграция заведения (`EstablishmentIntegration`)

- Принадлежит одному заведению.
- Хранит уникальный внешний ID, SHA-256-хеш ключа интеграции и признак активности.
- Исходный ключ промышленного окружения в БД не хранится.
- Ключ идентифицирует заведение и ограничивает им все операции интеграции.

### Позиция меню (`MenuItem`)

- UUID площадки и внешний ID заведения.
- Принадлежит ровно одному заведению.
- Изменяемые поля: название, описание, цена, доступность и активность.
- Цена — положительный `int64` в копейках, валюта для MVP всегда `RUB`.
- Позиция, отсутствующая в полном снимке меню, становится `active=false`, `available=false`.
- Изменение позиции меню никогда не изменяет уже созданные позиции заказа.

### Ссылка на пользователя (`UserReference`)

- Не отдельная таблица и не субъект безопасности.
- Непрозрачный строковый ID пользователя основной платформы.
- Сохраняется в заказе для связи данных.
- В автономном MVP вызывающая сторона может подставить любой ID; это явно не считается аутентификацией.

### Заказ (`Order`)

- UUID площадки и необязательный внешний ID заказа заведения.
- Принадлежит одному заведению и одному внешнему `user_id`.
- Неизменяемые после создания данные: пользователь, заведение, адрес, позиции, цены, сумма и хеш идемпотентного запроса.
- Изменяемые данные: состояние, причина отклонения, внешний ID заказа и время изменения.
- Не менее одной позиции; все позиции уникальны и принадлежат одному заведению.
- Сумма заказа равна точной сумме строк; проверяется переполнение `int64`.

### Позиция заказа (`OrderItem`)

Снимок содержит:

- исходный `menu_item_id`;
- `external_item_id`;
- название на момент создания;
- цену единицы;
- количество;
- сумму строки.

Исторический заказ не зависит от последующего переименования, изменения цены, недоступности или исключения позиции из меню.

### Машина состояний

| Текущее состояние | Разрешённое следующее |
|---|---|
| `pending` | `accepted`, `rejected` |
| `accepted` | `preparing` |
| `preparing` | `ready` |
| `ready` | конечное |
| `rejected` | конечное |

Повтор той же успешно применённой операции идемпотентен. Переход назад или через состояние возвращает `409 invalid_order_transition`.

### Модель согласованности

- В момент создания выбранные строки меню читаются под `FOR SHARE`.
- Синхронизация меню изменяет эти строки в транзакции и конфликтует с блокировкой.
- Если обновление завершилось первым, заказ проверяется по новым данным.
- Если создание заказа зафиксировалось первым, его снимок остаётся действительным независимо от последующего обновления меню.
- Логический признак доступности не расходуется при заказе. Поэтому два параллельных заказа могут пройти при `available=true`; это осознанное ограничение модели без количественных остатков.

## 7. API

Фактический контракт — `api/openapi.yaml`, OpenAPI 3.0.3. У пользовательского API нет схемы безопасности. API интеграции использует `Authorization: Bearer <integration-key>`.

Все ошибки имеют форму:

```json
{
  "error": {
    "code": "menu_item_unavailable",
    "message": "One or more menu items are unavailable",
    "details": {},
    "request_id": "..."
  }
}
```

### Пользовательский API

| Метод и путь | Назначение | Основные ответы |
|---|---|---|
| `GET /api/v1/establishments` | Активные заведения; `limit` 1–100, `offset >= 0` | `200`, `400` |
| `GET /api/v1/establishments/{id}/menu` | Активные позиции меню, включая `available=false` | `200`, `400`, `404` |
| `POST /api/v1/orders` | Создать заказ | `201`, повтор `200`, `400`, `404`, `409`, `500` |
| `GET /api/v1/orders/{id}?user_id=...` | Получить снимок и состояние заказа | `200`, `400`, `404` |
| `GET /api/v1/orders?user_id=...` | История заказов пользователя со страницами | `200`, `400` |
| `GET /health/live` | Процесс работает | `200` |
| `GET /health/ready` | API принимает запросы и видит PostgreSQL | `200`, `503` |

`POST /api/v1/orders` требует `Idempotency-Key` длиной 1–128. Семантический хеш запроса строится из пользователя, заведения, нормализованного адреса и отсортированных строк заказа.

### API интеграции заведения

| Метод и путь | Назначение | Основные ответы |
|---|---|---|
| `PUT /integration/v1/menu` | Полная идемпотентная замена проекции меню | `200`, `400`, `401` |
| `GET /integration/v1/orders?cursor=...&limit=...` | Получить изменённые заказы своего заведения | `200`, `400`, `401` |
| `POST /integration/v1/orders/{id}/decision` | `accepted` или `rejected`, передать `external_order_id` и причину | `200`, `400`, `401`, `404`, `409` |
| `PATCH /integration/v1/orders/{id}/status` | Перевести `accepted → preparing → ready` | `200`, `400`, `401`, `404`, `409` |

Курсор кодирует `(updated_at, order_id)` и трактуется клиентом как непрозрачное значение. Владелец всегда определяется ключом интеграции; заведение не передаёт ID заведения площадки и не может читать чужие заказы.

### Операторский API примера заведения

Это демонстрационный API, а не часть публичного контракта Avito:

- `GET /operator/v1/orders`;
- `POST /operator/v1/orders/{avito_order_id}/decision`;
- `PATCH /operator/v1/orders/{avito_order_id}/status`;
- `PATCH /operator/v1/menu-items/{external_item_id}`;
- `GET /health/live`;
- `GET /health/ready`.

У операторского API нет аутентификации только потому, что это локальная демонстрационная поверхность Compose.

## 8. Проектирование базы данных

### Таблицы

`establishments`

- UUID — первичный ключ.
- `name`, `kind`, `description`, `is_active`.
- `CHECK kind IN ('restaurant','cafe','store')`.
- `created_at`, `updated_at` как `timestamptz`.

`establishment_integrations`

- `establishment_id` — первичный и внешний ключ.
- Уникальный `external_id`.
- Уникальный 32-байтовый `api_key_hash`.
- `is_active` и метки времени.
- `ON DELETE RESTRICT`.

`menu_items`

- UUID — первичный ключ.
- Внешний ключ `establishment_id`.
- `external_id`, название и описание.
- `price_minor BIGINT CHECK (price_minor > 0)`.
- `currency CHAR(3) CHECK (currency = 'RUB')`.
- `is_active`, `is_available` и метки времени.
- `UNIQUE(establishment_id, external_id)`.

`orders`

- UUID — первичный ключ.
- Внешний ключ `establishment_id`.
- `user_id`, `delivery_address`.
- Необязательный `external_order_id`.
- `status` с ограничением БД `CHECK`.
- Необязательный `rejection_reason`.
- `total_price_minor BIGINT CHECK (total_price_minor > 0)`.
- `currency='RUB'`.
- `idempotency_key` и 32-байтовый `request_hash`.
- Метки времени.
- `UNIQUE(user_id, idempotency_key)`.
- Частичный уникальный индекс `(establishment_id, external_order_id)` для непустых значений.
- `CHECK` согласованности причины отклонения со состоянием.

`order_items`

- Составной первичный ключ `(order_id, line_no)`.
- Внешние ключи на заказ и позицию меню с `ON DELETE RESTRICT`.
- Снимки внешнего ID, названия, цены единицы, количества и суммы строки.
- `CHECK` положительных цен и сумм, количества 1–100.
- `UNIQUE(order_id, menu_item_id)`.

### Индексы под реальные способы доступа

- Частичный `(establishment_id, id) WHERE is_active` для чтения меню и проверки заказа.
- `(user_id, created_at DESC, id)` для истории пользователя.
- `(establishment_id, updated_at, id)` для курсора интеграции.
- Остальные необходимые индексы создаются уникальными ограничениями; дополнительных индексов «на всякий случай» нет.

### Миграции и демонстрационные данные

- Версионированные SQL-миграции `up/down`.
- Отдельный одноразовый сервис Compose применяет миграции после успешного `pg_isready`.
- `db/seed/demo.sql` идемпотентно добавляет только демонстрационное заведение и хеш известного ключа разработки.
- Автоматического создания схемы во время исполнения нет.
- API стартует после успешных миграций и заполнения данных.
- Все метки времени сохраняются в UTC, наружу отдаются как RFC 3339.

## 9. Проектирование интеграции

Выбрана модель опроса для заказов:

- Заведение инициирует передачу меню и опрос заказов.
- Основной API не делает сетевой вызов заведению внутри пользовательского запроса.
- Созданный заказ сначала надёжно фиксируется в PostgreSQL.
- Недоступность примера заведения не приводит к потере или откату пользовательского заказа.
- Опрос использует курсор, страницы и устранение дублей по ID заказа и времени версии.
- Курсор строится из `(updated_at, order_id)`, выбранных исходным запросом страницы, а не из повторно прочитанного изменяемого заказа. Конкурентное обновление может привести к безопасной повторной доставке, но не к пропуску другого заказа.
- Пример заведения повторяет опрос и несинхронизированное обновление меню с экспоненциальной задержкой до 30 секунд.
- Решение и состояние меняются синхронно: при сетевой ошибке оператор получает ошибку и повторяет запрос.
- Повторные решения и обновления состояния безопасны и идемпотентны.

Связи идентификаторов систем:

- `establishment_integrations.external_id` связывает заведение Avito с ID заведения.
- `(establishment_id, menu_items.external_id)` связывает позиции меню.
- `orders.id` — ID заказа Avito.
- `orders.external_order_id` — ID заказа в системе заведения.
- `orders.user_id` — внешний ID пользователя основной площадки.
- Тело заказа для заведения содержит внешние ID позиций и неизменяемые снимки.

## 10. Архитектура

### Архитектура исполнения

C4 уровня 2 показывает четыре основных контейнера:

- Веб-клиент — не реализуется, вызывает пользовательский API.
- API Avito.Кухни — модульный монолит.
- PostgreSQL — единственный долговременный источник истины.
- Сервис примера заведения — отдельный процесс, клиент интеграции и демонстрационный операторский API.

### Внутренняя структура основного API

- `transport/http`: сгенерированный интерфейс сервера, декодирование, проверка запросов и отображение ошибок.
- `application`: каталог, создание и отслеживание заказов, синхронизация меню и операции заведения.
- `domain`: деньги, правила снимка заказа, решения о доступности и переходы состояний.
- `persistence/postgres`: параметризованный SQL, транзакции и преобразование записей БД.
- `contract`: сгенерированные типы, сервер и клиент OpenAPI.
- `cmd`: конфигурация, сборка зависимостей, жизненный цикл и корректное завершение.

Направление зависимостей:

```text
cmd / адаптеры HTTP / PostgreSQL
              ↓
      прикладной слой
              ↓
    предметная область
```

Интерфейсы создаются только на реальных границах: транзакция PostgreSQL, часы при необходимости и HTTP-клиент интеграции. Универсальный каркас репозитория не вводится.

### Существенные зависимости

- `pgx/v5`: драйвер PostgreSQL, пул и транзакции; стандартной библиотеке всё равно нужен драйвер, а ORM для задачи избыточен.
- `oapi-codegen`: связь OpenAPI с интерфейсом сервера и клиентом интеграции на этапе компиляции; сгенерированный код изолирован и не редактируется вручную.
- Промежуточный обработчик проверки запросов по OpenAPI заранее проверяет сетевой контракт.
- Рабочий код использует стандартные `net/http`, `log/slog`, `context` и `encoding/json`.
- Каркас маршрутизации, ORM, контейнер внедрения зависимостей, библиотеки утверждений и моков и testcontainers не добавляются.
- Миграции, PlantUML и golangci-lint запускаются в контейнерах и инструментах с закреплёнными версиями, поэтому локальная установка `psql`, PlantUML и линтера не требуется.

API ограничивает размер тела, задаёт тайм-ауты HTTP, корректно завершается, пишет структурированные журналы и проверяет готовность. Рукописный код не содержит комментариев, пересказывающих очевидные действия.

|---|---|---|

| `REQ-P-003` → корректный заказ создаётся с точной суммой | `order_test.go`, тест API заказа | Фабрика предметной области и `CreateOrder` |
| `REQ-P-004` → устаревшие доступность или цена отклоняются | Табличные тесты предметной области и тест реальной БД | Транзакционный `CreateOrder` |
| `REQ-P-005` → переименование, новая цена и деактивация не меняют историю | Интеграционный тест снимка | Снимки `order_items` |
| `REQ-P-006` → одинаковые ключ и тело не создают дубль; другое тело конфликтует | Конкурентный интеграционный тест идемпотентности | Уникальное ограничение и хеш запроса |
| `REQ-P-007` → разрешены только заданные переходы | Чистые табличные тесты состояний и тесты API | Машина состояний предметной области |
| `REQ-P-008` → полная синхронизация добавляет, обновляет и деактивирует пропущенные позиции | Интеграционный тест реального PostgreSQL | Синхронизация меню |
| `REQ-P-009` → заведение получает заказ и обновляет его | Сквозной тест Compose | Сгенерированный клиент и API интеграции |
| `REQ-P-010` → конкурентное обновление выбранной строки не переносит курсор вперёд и не скрывает непрочитанный заказ | Детерминированный тест PostgreSQL с барьером между запросом страницы и загрузкой снимка | Запрос заказов интеграции и курсор |
| История пользователя → `ListOrders` соблюдает владельца, сортировку, `limit/offset` и `has_more` | HTTP-тест и интеграционный тест реального PostgreSQL | История заказов пользователя |
| Замена меню → пустой снимок атомарно деактивирует все позиции | Интеграционный тест реального PostgreSQL | Синхронизация меню |
| Повтор решения → точный повтор идемпотентен, другое тело и повторный внешний ID конфликтуют | Интеграционный тест реального PostgreSQL | Транзакция решения и уникальное ограничение |
| Ошибки примера → сетевые и неуспешные HTTP-ответы не подтверждают локальную операцию, обновление меню откатывается, курсор не продвигается | Модульные тесты с узким поддельным клиентом интеграции | Сервис примера заведения |
| `AVITO-003` → неверный ключ не даёт доступ к данным | HTTP-тесты отсутствующего, неверного и чужого ключа | Проверка ключа интеграции |
| Согласованность → обновление меню и создание заказа не дают смешанный снимок | Детерминированный тест БД с двумя соединениями | Блокировки строк и транзакция |
| Устойчивость → заказ создаётся без доступного примера заведения | Интеграционный тест приложения и последующий сквозной подбор | Интеграция через опрос |
| Контракт → каждый маршрут и ответ соответствует OpenAPI | Проверка спецификации, разницы генерации и схем ответов | OpenAPI и сгенерированные интерфейсы |
| Ограничения БД → отрицательные деньги, состояние и нарушенный внешний ключ отклоняются | Тесты миграций и ограничений на реальном PostgreSQL | Ограничения SQL |
| Compose → оба пути проходят через реальные HTTP | Сквозной тест | Полная система исполнения |
| `REQ-Q-005` → интеграционный набор не изменяет демонстрационную БД и не ломает сквозной тест | Проверка сохранности основного меню и последовательный запуск `make test-integration && make test-e2e` | Отдельная интеграционная БД и самоподготавливающийся сквозной тест |

Для каждого бизнес-среза соблюдается цикл:

1. Зафиксировать требование и критерий приёмки.
2. Написать целевой тест.
3. Запустить его и подтвердить ожидаемое падение.
4. Реализовать минимальное поведение.
5. Получить проходящий тест.
6. Выполнить рефакторинг без изменения требования.
7. Запустить все соответствующие проверки.

Чистые тесты предметной области не используют моки. HTTP-границы проверяются через `httptest`. Семантика PostgreSQL проверяется только на реальном PostgreSQL, поднятом Compose-профилем. Сквозной тест использует реальные контейнеры, миграции, демонстрационные данные и HTTP.

## 16. Упрощения и компромиссы

- **Модульный монолит вместо микросервисов:** одна предметная область и одна транзакционная БД; решение проще тестировать и защищать. При доказанной необходимости каталог или интеграцию заказов можно выделить по границам модулей.
- **Опрос вместо вебхука или очереди:** исключает распределённую транзакцию и потерю заказа при недоступности заведения. Цена — задержка и лишние запросы; дальнейшее развитие — таблица исходящих событий и подписанные вебхуки или очередь.
- **Без Redis в MVP:** ТЗ не запрещает Redis, но индексированного PostgreSQL достаточно для выбранного объёма, а создание заказа, идемпотентность и проверка доступности требуют долговременного транзакционного источника истины. Кэш добавил бы инвалидацию, устаревшие чтения и ещё одну зависимость исполнения без доказанного узкого места. Сначала нужно пакетно загружать списки заказов и обновлять меню, затем измерить нагрузку; позже Redis уместен как кэш публичного каталога с версией и TTL, но не как источник истины при создании заказа.
- **Полный снимок меню вместо API изменений:** простая атомарная семантика и восстановление после рассинхронизации. Для больших меню добавляются версионированные изменения.
- **Логическая доступность вместо количества остатков:** достаточно для заявленного MVP. Масштабирование потребует резервирования и отдельного источника истины об остатках.
- **Без локальных пользователей и аутентификации:** `user_id` является внешней ссылкой, как требует задание. В промышленном окружении шлюз аутентифицирует пользователя и подставляет доверенный ID.
- **Одно заведение на заказ:** сохраняет простое владение и транзакционную семантику. Заказ из нескольких заведений потребует разбиения на несколько заказов.
- **Ручное подключение:** демонстрационные данные доказывают интеграцию без лишнего административного продукта.
- **Заказ завершается в `ready`:** доставка после готовности находится вне MVP; жизненный цикл курьера должен быть отдельным контекстом.
- **Состояние примера заведения в памяти:** достаточно для демонстрации протокола; оно не входит в долговременный источник истины Avito.
- **Только RUB:** схема содержит валюту, но MVP не реализует конвертацию.
- **UUID и UTC:** ID площадки — UUID, метки времени — UTC/RFC3339.
- **Ключ разработки в Compose:** годится только для локальной демонстрации и явно маркируется как небезопасный для развёртывания.

## 17. Риски

| Риск | Контроль в MVP |
|---|---|
| Доступность в основном API может отстать от фактического остатка | Проверка в транзакции и право заведения отклонить только заказ `pending` |
| Полный снимок с ошибочно пропущенной позицией деактивирует её | Атомарная транзакция, итог синхронизации и явное описание семантики замены |
| Публичный `user_id` не обеспечивает приватность | README не называет это аутентификацией; в промышленном окружении нужен шлюз платформы |
| Опрос создаёт задержку и нагрузку | Курсор, страницы, настраиваемый интервал и задержка повторов |
| Перезапуск примера заведения теряет локальный кэш | Повторное чтение потока заказов; PostgreSQL основного сервиса остаётся источником истины |
| Конкурентное изменение выбранного заказа может сдвинуть курсор и пропустить непрочитанный заказ | Курсор фиксируется по паре исходной выборки страницы; детерминированный конкурентный тест допускает повторное чтение, но запрещает пропуски |
| Параллельные повторы идемпотентного запроса могут конфликтовать | Уникальное ограничение БД и конкурентный интеграционный тест |
| Демонстрационный ключ может случайно использоваться вне localhost | Явная маркировка, заполнение только в Compose и запрет запуска с известным ключом в промышленном окружении |

## 19. Воспроизводимость между AI-сессиями

До написания рабочего кода в репозитории создаются:

- `docs/spec.md` — полный текст этого утверждённого плана, требования, критерии приёмки, связь с проверками и архитектурные решения;
- `AGENTS.md` — короткая обязательная инструкция для любого нового агента;
- `docs/implementation-status.md` — текущее состояние выполнения плана.

`AGENTS.md` требует в начале каждой сессии:

1. Проверить `git status --short --branch` и сохранить несвязанные пользовательские изменения.
2. Полностью перечитать `backend-trainee-assignment-autumn-2026.md`.
3. Полностью перечитать `docs/spec.md`.
4. Полностью перечитать `docs/implementation-status.md`.
5. Сверить файл состояния с реальным кодом и результатами тестов.
6. Продолжать работу только с первого незавершённого критерия приёмки.

После каждого вертикального среза в `docs/implementation-status.md` фиксируются:

- текущий срез;
- закрытые требования и критерии приёмки;
- изменённые файлы;
- фактически запущенные команды и их результат;
- известные ошибки, ограничения и блокирующие проблемы;
- следующая детерминированная операция.

Исходное задание всегда имеет приоритет над `docs/spec.md`; план — над архитектурой, OpenAPI, тестами и реализацией. Если обнаружена фундаментальная ошибка, сначала обновляется соответствующий вышестоящий артефакт с объяснением причины, затем тесты и только после этого код. Файл состояния не является доказательством выполнения без подтверждающих команд и тестов.
